## Summary

The config-plugin code is correct. I found no defects in the plugin itself. What I verified independently:

- **Scratch prebuild.** I ran it outside the repo on Node 22.12 with `@expo/config-plugins` 9.0.17 and `expo` 52.0.49. The generated `AndroidManifest.xml` has `android:enableOnBackInvokedCallback="false"` on `<application>` and exactly one `<property android:name="android.window.PROPERTY_COMPAT_ALLOW_RESTRICTED_RESIZABILITY" android:value="true"/>` as a child of `<application>`. A second prebuild without `--clean` still had one property, so the plugin is idempotent on disk as well as in memory. `gradle.properties` has `android.compileSdkVersion=36` and `android.targetSdkVersion=36`. Toolchain: Gradle 8.10.2, buildTools 35.0.0, NDK 26.1.10909125, Kotlin 1.9.25.
- **Placement matches the Android docs.** https://developer.android.com/about/versions/16/behavior-changes-16 says this about predictive back: "temporarily opt out by setting the android:enableOnBackInvokedCallback attribute to false in the `<application>` or `<activity>` tag". About resizability it says: "To opt out a specific activity, declare the PROPERTY_COMPAT_ALLOW_RESTRICTED_RESIZABILITY manifest property: `<activity>`… If too many parts of your app aren't ready for Android 16, you can opt out completely by applying the same property at the application level: `<application>`". Both attributes are valid on `<application>`, and application level is the broader choice.
- **The mod actually runs.** Calling the registered `config.mods.android.manifest` directly applies the transform (see WR-03).
- **Tests and types pass.** `npx jest` gives 22 suites and 359 tests, all passing, which matches the updated counts in CLAUDE.md. `npx tsc --noEmit` is clean.
- **Lockfile spot-check.** Of the 47 changed entries, all are JS tooling (babel, `@expo/cli`, `@expo/package-manager`, `@expo/xcpretty`, and similar). No native-module versions changed. No engines constraint requires more than Node 20. Both `lightningcss` optional binaries are present.

The one blocker is a release gate, not a code bug. Nobody has compiled the native Android build at compileSdk 36 on AGP 8.6.0, and nobody has checked it on an API 36 device. The only native-adjacent evidence is `expo prebuild` plus `expo export`, and neither runs Gradle or AAPT2. The planned "preview build first" check also runs on a different EAS image than production (WR-01).

## Critical Issues

### CR-01: Native Android build and Android 16 runtime behavior are unverified (release gate)

**File:** `app.json:79-84`, `plugins/withAndroid16Compat.js:16-33`
**Issue:** The whole change rests on two unproven assumptions. RESEARCH-android.md rates both MEDIUM confidence (A2, A3):
1. AGP 8.6.0, which RN 0.76.9 pins, treats compileSdk 36 as a warning rather than an error. The official minimum for API 36 is AGP 8.9.1. The failure modes to watch for are AAPT2 failing to parse the android-36 `android.jar`, or any dependency that declares a minimum AGP.
2. On a real Android 16 device, the opt-out actually restores `ReactActivity.onBackPressed()`. That means back pops the expo-router stack instead of exiting the app, the app stays portrait on sw600dp, and the OAuth redirect returns correctly with targetSdk 36.

There is no JDK or Android SDK on this machine, and the SUMMARY lists no Gradle or EAS build. Under CLAUDE.md Rules 2 and 8 and the pre-ship checklist, this is a native-only change that web preview and Jest cannot verify, so it is not ready to ship. It is especially risky because targeting 36 without a working back opt-out makes the app exit on every back press for Android 16 users.
**Fix:** Before `eas submit`:
```bash
# build on the SAME image production will use (see WR-01)
npx eas build --platform android --profile production   # do not submit yet
```
1. Install the AAB via bundletool, or the APK from a preview build pinned to the same image, on an **API 36 emulator/device**.
2. Open Recipes, then a recipe detail, then press system back and do the back gesture. It must return to the list, not the launcher.
3. On an sw600dp API 36 emulator (Pixel Tablet), rotate the device. The app must stay portrait.
4. Cold start, run Google OAuth, and confirm it returns to the app.
5. Screenshot each step. If Gradle fails, apply the documented fallback (compileSdk 35 / targetSdk 36; see IN-02).

## Warnings

### WR-01: Android production image floats on `latest`, and the preview profile uses a different image

**File:** `eas.json:13-20` (preview), `eas.json:28-30` (production.android)
**Issue:** The research found that `latest` now resolves to `ubuntu-26.04-jdk-17-ndk-r27b-sdk-57`, an image built for SDK 57 that has changed since the last successful Android build in May 2026. This change pins iOS for reproducibility but leaves Android floating. The first compileSdk 36 build therefore changes two variables at once, and if it fails you can't tell whether the cause is the image or API 36. The `preview` profile sets no `image`, so it resolves to the SDK 52 default image (Ubuntu 22.04, Node 20, NDK r26). The research's "run a preview APK build first" step would then exercise a different toolchain from the production AAB, and a green preview build proves nothing about production. The same applies to iOS: preview and development default to `macos-sequoia-15.3-xcode-16.2`, not the pinned 26.2 image.
**Fix:** Pin Android production to the image that last succeeded (query EAS `resolvedImage` for Android build 19, or use `"sdk-52"`). Give `preview` the same Android and iOS images:
```json
"preview":    { "distribution": "internal", "ios": { "simulator": false, "image": "macos-sequoia-15.6-xcode-26.2" }, "android": { "buildType": "apk", "image": "<same as production>" } },
"production": { "ios": { "image": "macos-sequoia-15.6-xcode-26.2" }, "android": { "image": "<resolvedImage of build 19 or sdk-52>" } }
```
Add an assertion in `cross-platform-config.test.ts` that `build.preview.android.image === build.production.android.image`. Then update the CLAUDE.md line "Android production image stays `latest`".

### WR-02: `/android` is not gitignored, and a committed `android/` directory silently disables this plugin

**File:** `.gitignore:58` (only `/ios` is ignored), `CLAUDE.md:449`
**Issue:** If anyone runs `npx expo run:android` or `expo prebuild` in the repo root and commits the result, EAS treats the project as bare workflow and skips prebuild. That skips `withAndroid16Compat` and the `expo-build-properties` SDK 36 settings, so the manifest opt-out would disappear. All config tests would still pass, because they only read `app.json` and the plugin module. CLAUDE.md documents the trap ("Never run `expo prebuild` in the repo root") but doesn't close it, and the local `ios/` directory shows prebuild has already been run in the repo root before.
**Fix:** Add `/android` to `.gitignore`, next to `/ios`. Add a guard test:
```ts
it('android/ is not committed (would bypass config plugins on EAS)', () => {
  const gi = fs.readFileSync(path.resolve(__dirname, '../../.gitignore'), 'utf-8');
  expect(gi.split('\n').map((l) => l.trim())).toContain('/android');
});
```
Then reword the CLAUDE.md bullet.

### WR-03: The wiring test doesn't prove that the registered mod applies the transform

**File:** `__tests__/config/android16-compat-plugin.test.ts:85-88`
**Issue:** Test 6 only checks that `config.mods.android.manifest` is a function. If someone regressed the wrapper to `withAndroidManifest(config, (cfg) => cfg)`, or forgot to assign `cfg.modResults`, all 7 tests would still pass, because Tests 1–5 call `applyAndroid16Compat` directly. That is exactly the regression most likely to ship unnoticed. I confirmed that the registered mod can be invoked directly in Jest-compatible Node.
**Fix:** Replace Test 6 with:
```ts
it('Test 6 (wiring): the registered manifest mod applies the transform', async () => {
  const config = withAndroid16Compat({ name: 'homecook', slug: 'homecook' });
  const result = await config.mods.android.manifest({
    ...config,
    modResults: makeManifest(),
    modRequest: { platform: 'android', modName: 'manifest', projectRoot: '/tmp', platformProjectRoot: '/tmp', introspect: true },
    modRawConfig: config,
  });
  const app = result.modResults.manifest.application[0];
  expect(app.$['android:enableOnBackInvokedCallback']).toBe('false');
  expect(app.property).toHaveLength(1);
});
```

### WR-05: CLAUDE.md's new lockfile guidance is wrong for this repo and leads to `npm ci` failures on EAS

**File:** `CLAUDE.md:585` ("Use `npx expo install` so it stays in sync"), `.npmrc:5` (`save=false`)
**Issue:** The SUMMARY shows `npx expo install` updated `package.json` but not `package-lock.json`. In this repo, `npm install`, `npm install --package-lock-only` and even a deleted lockfile all left the lockfile unwritten, and it took an `npm shrinkwrap` rename to regenerate it. About 749 of the 1198 lock entries still have no `resolved`/`integrity` fields. Anyone who follows the new CLAUDE.md line will commit a `package.json` that is out of sync with `package-lock.json`, and EAS's `npm ci` will then fail with "package.json and package-lock.json are not in sync". In the worse case, the unpinned entries re-resolve to newer versions.
**Fix:** Replace the line with the procedure that actually worked, including a check step:
```
npx expo install <pkg>
npm install --package-lock-only   # if the lockfile is unchanged, fall back to: npm shrinkwrap && mv npm-shrinkwrap.json package-lock.json
git diff --stat package-lock.json # must be non-empty
npm ci --dry-run                  # must succeed
```
As a separate follow-up, regenerate the lockfile from a clean checkout so every entry has `resolved`/`integrity`.

### IN-02: The documented compileSdk fallback contradicts the new exact-match test

**File:** `__tests__/platform/cross-platform-config.test.ts:176`, `CLAUDE.md:445`
**Issue:** CLAUDE.md names "compileSdk 35 + targetSdk 36" as the fallback if AGP 8.6 fails. The test now requires `compileSdkVersion` to be exactly `36`, so applying the fallback turns CI red. Someone doing it under deadline pressure would also have to edit the test.
**Fix:** Either assert `targetSdkVersion === 36` and `compileSdkVersion >= 35`, or add a note to the CLAUDE.md fallback bullet that the fallback requires relaxing that assertion.

### IN-03: The plugin does little defensive checking

**File:** `plugins/withAndroid16Compat.js:17`, `:22`
**Issue:**
- `androidManifest.manifest.application[0]` and `p.$['android:name']` throw an unhelpful TypeError if there is no `<application>`, or if a `<property>` node has no attributes.
- An activity-level `android:enableOnBackInvokedCallback="true"` on MainActivity, for example from a future plugin, would override the application-level `false`. Nothing currently sets it.

**Fix:** Use `AndroidConfig.Manifest.getMainApplicationOrThrow(androidManifest)` and `p.$?.['android:name']`. Optionally, also delete `android:enableOnBackInvokedCallback` from `getMainActivityOrThrow(...)`.$.

**File:** `__tests__/config/app-config.test.ts:97-102`

The lock-step rule also forces an Android versionCode to be burned for an iOS-only resubmission, which is harmless but should be noted.

### IN-06: Release manifest carries template permissions that aren't declared in app.json

**File:** `app.json:55-57` (observed in the generated manifest from the scratch prebuild)
**Issue:** `android.permissions: ["INTERNET"]` doesn't strip the template's `READ_EXTERNAL_STORAGE`, `WRITE_EXTERNAL_STORAGE`, `SYSTEM_ALERT_WINDOW` and `VIBRATE`. This predates this change. Play doesn't reject for it, but the Data safety form and reviewers will see those permissions. Prebuild also warns that `userInterfaceStyle: automatic` needs `expo-system-ui` on Android.
**Fix:** In a separate change, add `"blockedPermissions": ["android.permission.READ_EXTERNAL_STORAGE","android.permission.WRITE_EXTERNAL_STORAGE","android.permission.SYSTEM_ALERT_WINDOW"]`.
