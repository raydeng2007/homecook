## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking issue] `npm install`/`npm ci` silently refuse to write `package-lock.json` in this environment, even when node_modules genuinely diverges from it**

- **Found during:** Task 3 Step A, immediately after `npx expo install expo-constants` and `npx expo install expo@~52.0.49`.
- **Issue:** `package.json` was correctly updated by the Expo CLI (which writes it directly, bypassing the repo's `.npmrc` `save=false`), and `node_modules/expo/package.json` correctly showed `52.0.49`. But `package-lock.json` on disk stayed byte-for-byte identical to its pre-task state (`expo@52.0.48`, no `expo-constants` root entry) after `npm install`, `npm install --force`, and `npm install --package-lock-only` — all reported "up to date" and made no write, even with `package-lock.json` deleted entirely first. Root cause: this repo's checked-in `package-lock.json` has no `resolved`/`integrity` fields on any package (a stripped/non-standard lockfileVersion 3 file, unrelated to this task), so this npm version's ideal-tree builder treats it as non-authoritative and, when it decides no `node_modules` changes are needed, skips the lockfile write step entirely — a genuine, reproducible npm quirk with this specific lockfile format, not something introduced by this plan.
- **Diagnosis performed:** Confirmed bash CAN write arbitrary files (ruled out a sandboxing issue); confirmed the same skip behavior persists with `dangerouslyDisableSandbox: true` (ruled out sandbox); confirmed `npm ci` against the *original* lockfile also silently re-resolved `@babel/generator` etc. to newer versions without ever touching the lockfile file (so this is not new behavior caused by this session — it means this lockfile has likely been silently non-functional for `npm ci`/`npm install` for some time, independent of this task).
- **Fix:** Reset to a clean baseline (`git checkout -- package.json`, restored the original `package-lock.json` from a local backup, `npm ci`), re-ran the two required `npx expo install` commands from LD-5, then used `npm shrinkwrap` (which does perform a real write) to regenerate `package-lock.json`, and immediately renamed `npm-shrinkwrap.json` -> `package-lock.json`. Verified afterward that `node_modules` did not drift further (checked `@babel/generator` and `expo` versions before/after) and re-ran `expo-doctor`, `tsc --noEmit`, and the full Jest suite — all pass.
- **Scope of the resulting diff:** Because the checked-in lockfile was already stale relative to `node_modules` (unrelated to this task — see below), the regenerated `package-lock.json` diff is larger than a minimal "add expo-constants, bump expo" delta: 2 added entries, 4 removed entries, 195 changed entries (mostly transitive `@babel/*` and similar packages moving from their 5-month-old pinned versions to their actual currently-resolved versions). `package.json`'s own diff remains exactly the 2 intended lines (`expo` bump, `expo-constants` addition) — no other direct dependency ranges were touched.
- **Files modified:** `package-lock.json` (regenerated), `package.json` (unchanged from the originally intended 2-line diff).
- **Not committed:** per instructions, left unstaged for user review.

### Deferred / Flagged Issues (not fixed — out of scope)

**1. `package-lock.json` has been silently out of sync with actual installed `node_modules` for an extended period, independent of this task.** The pre-task lockfile (last touched 2026-05-19 per its mtime) had no `resolved`/`integrity` fields for any package and, in this npm/environment combination, `npm install` / `npm ci` do not keep it in sync — they silently re-resolve to registry-latest-matching versions in `node_modules` without ever rewriting the lockfile. This means `npm ci` in CI or on a fresh machine may not reproduce exactly what any given developer's `node_modules` currently contains, and it may have been silently drifting since May. This is a pre-existing condition, not caused by this plan, but is worth a follow-up (e.g., regenerating and re-pinning the lockfile with `resolved`/`integrity` fields via a normal `rm -rf node_modules && npm install` on a clean checkout, verified reproducible with `npm ci`). Logged here rather than fixed, since it is outside this plan's Android API 36 scope and the plan's `<out_of_scope>` explicitly limits changes to the two named `npx expo install` commands.
